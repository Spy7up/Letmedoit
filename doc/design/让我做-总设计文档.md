## 1. 产品定位

### 1.1 一句话

**别人让你做的小事，说一遍就够。**

「让我做」是给熟人关系（家人、室友、情侣、帮手）用的**口头委托承接箱**：说出口的那一刻就落成一条任务，自动提醒相关的人，做完对方第一时间知道。

### 1.2 解决的问题

| 现状痛点 | 产品对策 |
|---|---|
| 微信里口头交代，消息一刷就没 | 委托落成结构化任务，不依赖聊天记录 |
| 谁该做什么、什么时候要，全靠记 | 截止时间 + 站内提醒，打开小程序就能看到 |
| 催人尴尬，问"弄了吗"像查岗 | 状态即答案：谁在做、谁做完了，不必开口问 |
| 一句"你俩一起弄一下"，最后只有一个人动 | 多人任务 + 每人独立完成状态，谁没动一目了然 |
| 做了没人知道，没有正向反馈 | 完成后自动通知委托人，形成"被看见"的闭环 |
| 通用待办 App 是"自己的事"，没有关系维度 | 任务天生绑定几个人，社交压力即执行力 |

### 1.3 差异化（决定 UI 取舍）

1. **以"关系"组织，不以"项目"组织**。只有"我收到的 / 我发出的"，信息架构两层：任务列表 → 任务详情。
2. **多人不是"协作"，是"分摊"**。一条任务交给 1~10 个人，每人只管自己那一格，无子任务拆解。
3. **双方视角对称**。同一任务在委托人眼里是"我在等"，在参与者眼里是"我要做"，文案、按钮、颜色随角色变化。
4. **文案去企业化**。用"等 TA 接单""我这部分做完了""催一下"，不用"负责人""验收"。
5. **轻量优先**。布置一条任务 ≤ 4 次点击，其余全部有默认值。

### 1.4 明确不做

- 不做群聊式协作（无讨论区、@、评论流，沟通回微信）
- 不做子任务拆解 / 互相指派、重复任务、优先级、标签
- 不做积分、排行榜、打卡日历
- 不做陌生人社交，帮手必须先建立关系
- **不做微信订阅消息推送**（2026-10-26 已整条链路移除，通知只保留站内信 + 分享卡片触达）

## 2. 用户角色与关系模型

### 2.1 角色

| 角色 | 定义 | 权限 |
|---|---|---|
| 未登录访客 | 首次进入、未授权 | 仅可浏览引导页，任何写操作跳登录 |
| 登录用户 | 已微信登录并完成资料 | 全部功能 |
| 委托人 Creator | 某条任务的布置方（一条任务只有一个） | 编辑（受限）、撤回、删除（仅已撤回）、催办、加人、查看所有人进度与备注 |
| 参与者 Participant | 被委托人指定执行的人（1~10 个） | 接受 / 拒绝 / 完成自己那格（附备注与凭证）、查看其他参与者状态 |

两条关键规则：

1. **角色是任务维度的，不是账号维度的**。
2. **委托人可以把自己加进参与者**，此时同时拥有两套权限（可撤回 + 可完成自己那格）。

### 2.2 帮手关系

- 双向对等，一条 `t_helper` 记录代表一对关系（存储双写两行，按 memberId 查询）
- 建立方式：**分享邀请卡片**（主路径）或 **6 位邀请码**（面对面场景；邀请码注册时自动生成，字符集去掉 `0/O/1/I`）
- 输邀请码是**直接成为帮手**，不需对方确认；扫码/卡片进入需对方确认
- 解除关系：二次确认；有进行中任务时提示但不阻断

## 3. 核心业务流程

### 3.1 主流程（单人）

```
①  布置     委托人：选 1 人 → 标题/描述/截止/提醒 → 选完成条件 → 发布（写站内通知）
②  待接受   参与者列表红点 + 通知中心「任务委托通知」
            ├── 接受 ──► ③ 进行中 ──► 附备注/凭证标记完成 ──► ④ 已完成（通知委托人）
            └── 拒绝（填理由）──► 已拒绝（终态）
            到点未完成 ──► 已逾期（红标 + 提醒）
```

### 3.2 多人委托的两种完成条件

- `completionMode = 2 全员完成`：最后一人完成 → 任务完成，发「全员完成通知」
- `completionMode = 1 任一人完成`：第一人完成 → 整单完成，其余 `pending/accepted` 参与者自动置 `skipped`（不追责、不再提醒）

### 3.3 定时任务（预约）

- 发布时可设 `startTime`，任务为「预约中」，参与者**不可接受**
- 到点后 `TaskScheduleJob`（每分钟）翻成「待接受」；`startNotifyFlag=1` 时发「任务开始通知」
- 预约中可撤回、可编辑、可加人；编辑页关掉开始时间点开关 → 立即退回「待接受」

### 3.4 状态机（唯一定义源）

**两层状态**：参与者状态（每人一格，落库）+ 任务聚合状态（写入时重算落库，供列表与通知）。

参与者状态（`t_task_participant.status`）：`0 待接受 / 1 已接受 / 2 已完成 / 3 已拒绝 / 4 已跳过`

| 当前 | 事件 | 下一状态 | 触发方 |
|---|---|---|---|
| — | 被加入任务 | 0 待接受 | 委托人 |
| 0 | accept | 1 已接受 | 该参与者 |
| 0 | reject（必填理由） | 3 已拒绝 | 该参与者 |
| 1 | complete（可附备注/图） | 2 已完成 | 该参与者 |
| 0/1 | 他人完成且模式为任一人 | 4 已跳过 | 系统 |

任务聚合状态（`t_task.status`）：`0 预约中 / 1 待接受 / 2 进行中 / 3 已完成 / 4 已拒绝 / 5 已撤回`

```
定时未开始且无人动作                  → 0 预约中
全部 rejected/skipped                 → 4 已拒绝
全员 done                             → 3 已完成
any 模式且有人 done                   → 3 已完成
有人 accepted 或 done                 → 2 进行中
else                                  → 1 待接受
```

- **逾期是派生不是状态**：`status ∈ {1,2} AND deadline < now`，查询用 `overdueFlag=true` 传入
- `5 已撤回` 由委托人直接写入，不参与聚合
- 聚合状态的判定在服务端 `TaskManager` 一处，前端不重算，只读 `status` 与 `canXxx` 权限位
- **并发安全**：所有状态流转都是 `UPDATE ... WHERE status = 旧值`，受影响行数为 0 时提示「任务状态已变化，请刷新后重试」

### 3.5 权限位（服务端算，前端只读）

| 权限位 | 规则 |
|---|---|
| `canEdit` | 预约中/待接受：不限次；进行中：**只一次**（`t_task.edit_count` 只在进行中累加）；其余 false。编辑只接受标题/交代内容/完成条件/截止/提醒，参与者与定时生效不可改 |
| `canCancel` | 预约中/待接受/进行中，仅委托人 |
| `canDelete` | 仅委托人 + 已撤回；删除为逻辑删除，`t_task` + `t_task_participant` + `t_task_notice` 三表一起，`t_task_event` 保留追溯 |
| `canRemind` | **只有委托人**且任务进行中；催办限频 60 秒，超频返回 `code=30001`「刚催过啦」 |
| `canAddParticipant` | 任务未开始前，≤10 人，必须都是帮手；已完成后禁止追加 |
| `canAccept/canReject/canComplete` | 仅该参与者自己那格 |

### 3.6 时间与提醒规则

| 项 | 规则 |
|---|---|
| 截止时间 | 「某个时间点」精确到分钟，不早于现在 + 2 小时；「某一天」= 当天 23:59:59 |
| 提醒 | 以截止时间为基准往前推 `remindMinutes`；已过去不补发；`TaskScheduleJob` 扫 `remind_time`，只发未完成者，发完清空防重 |
| 开始时间点 | 可选，须晚于现在且早于截止；「某一天」任务须早于当天 22:00 |
| 逾期重复提醒 | 每 12 小时最多 1 次，最多 2 次 |
| 时间格式 | 后端统一 `yyyy-MM-dd HH:mm:ss`（东八区）；前端 `adapt.js` 负责转换 |

### 3.7 异常与边界

| 场景 | 处理 |
|---|---|
| any 模式有人完成 | 其余 pending/accepted 自动 skipped，不再提醒 |
| 全部拒绝 | 聚合为已拒绝，通知委托人 |
| 部分拒绝 + 部分完成（all 模式） | 任务继续；rejected 不计入分母，进度 `done/(total-rejected)` |
| 帮手已解除但仍有进行中任务 | 任务保留可完成，列表标注「已不是帮手」，禁止新建 |
| 重复提交 | 前端按钮 loading + 幂等键 `clientRequestId` |

## 5. 数据模型

### 5.1 通用约定

- 接口返回统一信封：`{ code, level, msg, ok, data, dataType }`，`code = 0` 成功
- 后端 Long ID 由前端 `adapt.js` 转 string（规避 JS 精度丢失）
- 时间出/入参统一 `yyyy-MM-dd HH:mm:ss`（全局 Jackson 配置 + `@JsonFormat`）
- 布尔字段以 `flag` 结尾（`deletedFlag`/`deleted_flag`）
- 枚举型表字段注释必须列出全部取值

### 5.2 核心表

| 表 | 说明 | 关键索引 |
|---|---|---|
| `t_wx_member` | 会员主表 | `uk_open_id`（兜住并发注册）、邀请码唯一 |
| `t_helper` | 帮手关系（双写两行） | `uk_member_helper` |
| `t_helper_request` | 帮手申请（0 待处理 1 已同意 2 已拒绝） | `idx_to_status` |
| `t_task` | 任务 + 聚合状态；`edit_count`/`remind_time`/`client_request_id`/`start_notify_flag` | `idx_creator_status`、`idx_status_deadline`、`idx_remind_time` |
| `t_task_participant` | 参与者（一人一格；`remark`/`complete_images` JSON/`reject_reason`） | `uk_task_member`、`idx_member_status` |
| `t_task_event` | 任务事件（append-only，时间线 + 追溯） | `idx_task` |
| `t_task_notice` | 站内通知（**不是 `t_notice`**，那是框架公告表） | `idx_member_read` |
| `t_app_feedback` | 问题与反馈 | `idx_status_time`、`idx_type_time`、`idx_member_time` |
| `t_app_version` | 小程序版本 | `uk_type_version`、`idx_type_current` |
| `t_app_agreement` | 协议正文（user/privacy 各一条 enabled） | — |
| `t_content_check` | 内容安全送检记录 | — |

注意：`t_task` 上没有 `assignee_id`，列表查询按 `t_task_participant` 关联，`role` 由是否 creator 决定。

### 5.3 通知 `fields_json` 渲染契约

`[{label, value}]`，顺序即展示顺序；最多 4 行，**第一行永远是任务名称**。前端 `services/notice.js` 只读不拼。

## 6. 接口契约（sa-app，前缀 `/api`）

| 项 | 说明 |
|---|---|
| 鉴权 | `App-Token: Bearer <token>`，`AppInterceptor` 统一校验 |
| 免登录 | `/api/auth/login`、`/api/version/current`、`/api/agreement/*`（白名单在 `AppMvcConfig`） |
| 当前用户 | 服务端从 token 取，**不接受前端传 memberId** |
| 分页 | `pageNum` / `pageSize`（上限 500） |

### 6.1 任务

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/task/query` | 列表；`role 1收到/2发出`，`status 0~5`，`overdueFlag` 只看逾期 |
| GET | `/api/task/get/{taskId}` | 详情（含 participants、me、canXxx、events） |
| GET | `/api/task/summary` · `/api/task/stats` | 当日摘要 / 个人统计 |
| POST | `/api/task/add` | `memberIds[]`（1~10 且都是帮手）、`completionMode 1任一人/2全员`、`deadline`、`startTime?`、`remindMinutes` |
| POST | `/api/task/update` | 编辑；进行中仅一次 |
| POST | `/api/task/accept` · `reject` · `complete` · `cancel` · `delete` · `remind` · `participant/add` | 状态流转，均返回最新 `TaskDetailVO` |

### 6.2 帮手

`GET /api/helper/list?keyword=`、`GET /api/helper/request/list`、`POST /api/helper/request/add|accept|reject`、`GET /api/helper/invite`、`POST /api/helper/invite/accept`、`POST /api/helper/remove`。

### 6.3 通知

`POST /api/notice/query`（含 `unreadCount`）、`GET /api/notice/unread-count`、`POST /api/notice/read`（`allFlag` 全读，返回剩余未读数）。

### 6.4 账号 / 反馈 / 版本 / 文件

- `GET /api/member/info`、`POST /api/member/profile`、`POST /api/member/delete`（注销：匿名化 + 逻辑删帮手关系，任务/通知/协议记录保留显示「已注销用户」，旧 token 立即失效 30007）
- `GET /api/feedback/type/list`、`POST /api/feedback/add`（type 1~4，content ≤500 过内容安全，images ≤3 必须走上传后的公网 URL）
- `GET /api/version/current`（免登录；未配置时 version 为空串、code 仍 0）
- `POST /api/file/upload`（bizType：`avatar`/`task-image`/`feedback-image`，落 COS `public/app/{bizType}/`，公网可读）

### 6.5 关键错误码

| code | 含义 | 前端行为 |
|---|---|---|
| 0 | 成功 | — |
| 30001 | 业务提示（如催办限频） | toast 服务端 message |
| 30007 | 登录态失效 | `wx.login` 静默换 token 并重放一次 |
| 30002/30005 | 参数错误 / 无权限 | toast |

## 7. 通知体系（仅站内信）

所有通知只写 `t_task_notice`，由消息中心展示；首次触达靠分享卡片。**微信订阅消息链路已整体移除，不要加回。**

| 模板 key | 触发 | 收件人 |
|---|---|---|
| `TASK_ASSIGNED` | 布置 / 预约到点转待接受 / 被追加 | 全部参与者（不含委托人） |
| `TASK_START` | 开始时间到点（开关开启） | 全部参与者（不含委托人） |
| `TASK_REMIND` | 到期提醒 / 手动催办 | 未完成的参与者 |
| `TASK_EDITED` | 委托人编辑后 | 全部参与者 |
| `TASK_CANCELLED` | 委托人撤回后 | 全部参与者（不含委托人） |
| `TASK_COMPLETED` | 有人完成 | 委托人 |
| `TASK_ALL_DONE` | 全员完成 | 委托人 + 全体参与者 |

四条纪律：标题用「名词 + 通知」；标签 3~4 个且第一个永远是任务名称；值要能独立成立；不塞隐私内容。
`NoticeTemplateEnum` 只有 `key`+`title`；`TaskNoticeService.insertBatch` 直接落库。

触达路径：消息中心（可回看 + 红点）→ 首页铃铛红点 + banner 逾期提示 → 详情页 onShow 刷新 → 分享卡片。

## 8. 登录与账号体系

> 早期《一键登录改造方案》中的 `Member-Token`、微信支付（P3）均未落地；以下为**实际实现**。

- 两套 Sa-Token 体系物理隔离：后台 `StpUtil`（`Authorization`，Redis `satoken:login:*`）；小程序 `StpLogic("app")`（Bean `stpAppLogic`，`App-Token`，Redis `satoken:app:*`）。会员 token 塞进 `Authorization` 也访问不了后台。
- 会员配置：`activeTimeout = -1`（不冻结）、单端登录、30 天 + auto-renew；前端收 30007 时静默 `wx.login` 续期。
- 登录链路：`wx.login` → `POST /api/auth/login {code}` → `jscode2session` 换 openid → 查/建 `t_wx_member` → 签发 token。`wx.miniapp.mock=true` 时用 `mock_md5(code)` 当 openid（本地联调与 e2e 用）。
- 昵称头像：**不调 `wx.getUserProfile`**。为空或占位时服务端生成「用户 + 4 位大写字母数字」；头像只走 `chooseAvatar` + `/api/file/upload`，临时路径绝不入库。
- 手机号：`/api/auth/phone` 代码就绪，但小程序端未调 `wx.getPhoneNumber`，实际未采集。
- 内容安全：文本 `msgSecCheck`（同步）、图片 `mediaCheckAsync`（异步，消息推送回传结果，违规由 `ContentTakedownService` 摘除）。详见 `letmedoit-api/docs/CONTENT_SECURITY.md`。
- 安全清单：`session_key` 禁下发/落库/日志；code 一次性；openid/手机号脱敏；登录按 IP + openid 限流（30 次/分）。

## 9. UI 设计规范

### 9.1 风格

**暖、轻、有人味**：米白纸感底 + 珊瑚橘行动色 + 大圆角卡片 + 极轻阴影 + 液态玻璃点缀。三条执行原则：一屏一决策；状态用色不用形；动作永远在拇指区（`env(safe-area-inset-bottom)`）。

### 9.2 配色令牌

| 令牌 | 色值 | 用途 |
|---|---|---|
| `--brand` / `--brand-ink` / `--brand-soft` | `#FF6B4A` / `#D64C28` / `#FFEDE7` | 主按钮、选中态、进行中 |
| `--mint(-soft)` | `#17A67C` / `#E4F6EF` | 已完成 |
| `--amber(-soft)` | `#E08A00` / `#FDF3E2` | 待接受 |
| `--violet(-soft)` | `#6B5BD2` / `#EFECFC` | 预约中 |
| `--danger(-soft)` | `#D64545` / `#FCEBEB` | 逾期、危险操作 |
| `--ink-1/2/3` | `#1E1B18` / `#6B625B` / `#A69C93` | 主/次/辅助文字 |
| `--line` / `--bg` | `#EFE9E3` / `#F7F4F1` | 分割线 / 页面底 |

### 9.3 字体与尺度

系统默认字体。H1 40rpx/600、H2 34rpx/600、正文 28rpx、辅助 24rpx、标签 22rpx/500。
间距基准 8rpx；页面左右边距 32rpx；卡片圆角 32rpx、内边距 26rpx、间距 22rpx；tag/chip 圆角 999rpx；阴影仅卡片 `0 4rpx 16rpx rgba(30,27,24,.05)`。

### 9.4 液态玻璃（全页最多两处：首页 banner + 悬浮 tabBar）

- 折射源用 `radial-gradient` 色斑（`#FF5F35/#1FC49B/#FFAE7E/#FFD0C0`），**不用** `filter: blur()` 圆形（部分安卓 WebView 不生效）
- 玻璃层：`backdrop-filter: blur() saturate()` + 半透明白渐变 + 内外高光
- 必须给降级：`@supports not (backdrop-filter: blur(1px))` 时改不透明渐变
- 玻璃里放结论不放列表；不给卡片/列表项加 blur
- 自定义 tabBar：每 tab 页 `onShow` 同步 `selected`；页面底部留 `tab-space`；点击先切图标再 `switchTab`

### 9.5 状态设计（每页必须实现）

骨架屏（3 张卡）、下拉刷新、空态（收到/发出/筛选/消息 4 种文案）、错误重试、无网络黄条、提交 loading、成功轻震动 + toast。

### 9.6 文案语气

| 场景 | ✅ | ❌ |
|---|---|---|
| 发布成功 | 已交给小王、陈陈，等 TA 们接单 | 任务创建成功 |
| 空列表 | 暂时没人麻烦你 | 暂无数据 |
| 完成成功 | 干得漂亮，已告诉妈妈 | 操作成功 |
| 任一人完成 | 你抢先做完了，其他人不用做了 | 任务已结束 |
| 被拒绝 | 小王这次没接，换个人？ | 任务被拒绝 |

### 9.7 状态文案映射

唯一出口在 `miniprogram/constants/task.js`（预约中/待接受/进行中/已逾期/已完成/已拒绝/已撤回 + 参与者 5 态），色值与 9.2 一致；文案服务端用 `AppDictService.label()`（字典优先、枚举 desc 兜底）。

## 10. 版本管理

- **唯一来源**：`GET /api/version/current`（免登录白名单 `AppMvcConfig.VERSION_PUBLIC_PATHS`）；页面禁止出现版本字面量
- 表 `t_app_version`：同端只应一行 `current_flag=1`；**发布 = 事务内两步**（同端全置 0 → 目标置 1），不给 `current_flag` 建唯一索引
- 前端 `services/version.js#current()`：内存 + `lmd_app_version` 两级缓存，拿不到留空不挡页面
- **协议版本 ≠ 小程序版本**：协议走 `t_app_agreement`，变更要重新征得同意；不要合并
- 发版顺序：**先发小程序包，再发布版本记录**
- 预留字段 `min_base_lib` / `force_update_flag` 本期只落库不生效
- 后台管理界面本期不做；后台接入时按 `sa-admin/module/business/version/` 新模块建（sa-admin 不依赖 sa-app，共用同表，类名各自独立）

## 11. 问题与反馈

- 类型：1 功能建议 / 2 使用问题 / 3 内容违规 / 4 其他（字典 `FEEDBACK_TYPE`，后台改词小程序不发版）
- 内容 ≤500 字过 `msgSecCheck`；图 ≤3 张必须走 `/api/file/upload`（`feedback-image`）的公网 URL，服务端 `assertImagesTrusted` 校验送检记录
- 提交后只提示「收到了」，用户看不到处理进度；违规下架静默不通知
- 举报入口：任务详情「举报这条任务」→ 反馈页 `?type=3&content=` 预选预填
- 后台客服界面本期不做；接入设计（模块结构、权限码 `feedback:query/reply/update/export`、状态流转 0→1→2 / 直接关闭 3、列表排序 `(status=0) DESC, create_time DESC`）已定稿，照做即可
- **命名坑**：sa-base 已有 `module/support/feedback`，新模块一律 `App*` 前缀、字段 `appFeedback*`（`@Resource` 按字段名注入）

## 12. 文件上传与对象存储

- 链路：`POST /api/file/upload`（`AppFileService`）→ sa-base `IFileStorageService`（S3 兼容）→ 目录固定 `public/app/{bizType}/`。**不能用 `FileService.fileUpload`**（固定 `private/`，返回 1 小时过期预签名 URL）
- 腾讯云 COS：桶 `letmedoit-1308200923`（广州）；SecretId/Key 只走环境变量；**必须 `path-style-access: false`**（新桶只支持 virtual-hosted-style）
- 前端临时路径（`chooseAvatar`/`chooseMedia`）必须先 `services/file.js#uploadImage()` 换公网 URL 再提交，绝不入库
