# 问题与反馈（sa-app）

> 入口：小程序「我的 → 问题与反馈」 · 后端模块 `sa-app/module/feedback` · 建表脚本 `docs/sql/init/letmedoit_init.sql`（全量）/ `docs/sql/updates/2026-10-27/01_feedback.sql`（增量）
> 本期只做**小程序提交 + 落库**，后台客服界面不做，但表、索引、状态流转、权限码都按后台需要设计好了。

---

## 1. 用户能做什么

| 项 | 规则 |
|---|---|
| 反馈类型 | 必选，1 功能建议 / 2 使用问题 / 3 内容违规 / 4 其他（字典 `FEEDBACK_TYPE`） |
| 反馈内容 | 必填，≤ 500 字，提交前过微信内容安全 `msgSecCheck` |
| 图片 | 选填，最多 **3 张**；必须先走 `/api/file/upload`（bizType=`feedback-image`）换成公网 URL |
| 联系方式 | 选填，≤ 64 字（后台回复用，小程序暂不采集，字段先留着） |
| 提交后 | 只提示「收到了，谢谢你」，不跳转二级页；用户看不到处理进度（本期不做） |

## 2. 数据表 `t_app_feedback`

```sql
feedback_id     主键
member_id       提交人会员ID
type            反馈类型 1功能建议 2使用问题 3内容违规 4其他
content         反馈内容
images          JSON 数组字符串，最多 3 张公网 URL
contact         联系方式（选填）
status          处理状态 0待处理 1处理中 2已解决 3已关闭
reply_content   处理回复（后台填）
reply_member_id 处理人（后台员工ID）
reply_time      回复时间
deleted_flag    逻辑删除
create_time / update_time
```

索引按后台列表的真实查询路径建：

| 索引 | 支撑的查询 |
|---|---|
| `idx_status_time (status, create_time)` | 「待处理」工作台默认列表，按时间倒序 |
| `idx_type_time (type, create_time)` | 按类型筛选（内容违规优先处理） |
| `idx_member_time (member_id, create_time)` | 将来做「我的反馈」时按人查 |

> **为什么图片是一列 JSON 而不是独立表**：和 `t_task.images`、`t_task_participant.complete_images` 保持同一种存法。反馈图从来不会单独查询、也不会分页，独立表只多一次 join。3 张 × 500 字符 ≈ 1.6KB，`VARCHAR(2000)` 够用。

## 3. 接口（sa-app，前缀 `/api`，需登录）

| 方法 | 路径 | 入参 | 返回 |
|---|---|---|---|
| GET | `/api/feedback/type/list` | — | `[{ value, label }]` |
| POST | `/api/feedback/add` | `{ type, content, images?, contact? }` | `Long`（反馈ID） |

提交体：

```json
{
  "type": 2,
  "content": "完成任务后图片没显示出来，机型 iPhone 14",
  "images": ["https://letmedoit-1308200923.cos.ap-guangzhou.myqcloud.com/public/app/feedback-image/xxx.jpg"]
}
```

校验与错误：

| 场景 | 返回 |
|---|---|
| 类型不在枚举内 | `30002` 参数错误「反馈类型不对」 |
| 内容为空 | 「说说遇到的情况吧」 |
| 内容命中微信内容安全 | 「反馈内容含有不适合发布的内容…」 |
| 图片不是走过上传的地址 | 「有图片未通过安全检测，请重新上传」 |
| 未登录 | `30007`，小程序侧静默重登一次 |

`type/list` 的文案取自字典，**后台改一个词小程序不用发版**；字典缺失时退回枚举 `desc`，接口永远不返回空列表。

## 4. 图片与内容安全

复用现有链路，没有新造轮子：

```
wx.chooseMedia → services/file.js#uploadImage(path, 'feedback-image')
   → POST /api/file/upload（AppFileService，路径 public/app/feedback-image/）
   → 上传成功即送微信 mediaCheckAsync（ContentBizTypeEnum.FEEDBACK_IMAGE）
   → 违规结论回传后 ContentTakedownService 从 t_app_feedback.images 里摘掉
```

三条硬约束（都在服务端再判一遍，不信任客户端）：

1. 只收公网 `http(s)`，微信临时路径（`wxfile://`、`http://tmp`）一律丢弃；
2. 最多 3 张，超出丢弃不报错；
3. 图片地址必须能在 `t_content_check` 里查到送检记录（`assertImagesTrusted`）。

> 内容违规类反馈是审核红线，只有后台能看，所以下架时**不给用户发通知**，静默移除即可。

## 6. 后台接入设计（这期不做，照这个做即可）

### 6.1 放在哪个模块

sa-admin **不依赖** sa-app，后台要在 `sa-admin` 里新建同表模块（共用同一张 `t_app_feedback`）：

```
sa-admin/src/main/java/net/lab1024/sa/admin/module/business/feedback/
├── constant/FeedbackStatusEnum.java      # 可以复用 sa-app 的定义，也可以各留一份
├── controller/FeedbackController.java
├── service/FeedbackService.java
├── dao/FeedbackDao.java
├── domain/{entity,form,vo}/
sa-admin/src/main/resources/mapper/business/feedback/FeedbackMapper.xml
```

> 不要试图让 sa-admin 依赖 sa-app：两套 token、两套账号体系，依赖会连带把 `AppInterceptor` 的配置带进后台。

### 6.2 接口与权限码

| 方法 | 路径 | 权限码 | 说明 |
|---|---|---|---|
| POST | `/feedback/query` | `feedback:query` | 分页列表，入参见下 |
| GET | `/feedback/get/{feedbackId}` | `feedback:query` | 详情（含图片、提交人） |
| POST | `/feedback/reply` | `feedback:reply` | 填 `replyContent` + `status` |
| POST | `/feedback/update/status` | `feedback:update` | 只改状态（关闭重复反馈） |
| GET | `/feedback/export` | `feedback:export` | 导出 Excel（可选） |

菜单三个按钮的 `api_perms` 与上表一一对应，角色里勾选后生效。

### 6.3 列表查询参数（`FeedbackQueryForm extends PageParam`）

```java
private Integer type;        // 反馈类型，空为全部
private Integer status;      // 处理状态，空为全部
private String keyword;      // content / contact 模糊
private Long memberId;       // 指定用户
private LocalDate startDate; // create_time 下界
private LocalDate endDate;   // create_time 上界（含当天）
```

XML 要点：`deleted_flag = 0` 必带；`keyword` 用 `INSTR`；排序 `status = 0 优先` 再 `create_time DESC`（待处理排前面，客服不用翻页找）。

```sql
ORDER BY (status = 0) DESC, create_time DESC
```

### 6.4 状态流转

```
0 待处理 ──受理──► 1 处理中 ──回复──► 2 已解决 ──► 终态
   └────────直接关闭（重复/无需处理）────► 3 已关闭
```

- 回复时必填 `replyContent`，同时写 `reply_member_id` / `reply_time`；
- 允许从任意非终态直接关闭，但**已解决只能由回复动作进入**（统计口径干净）；
- 状态值一律 `UPDATE ... WHERE status = 旧值`，避免两个客服同时处理互相覆盖。

### 6.5 将来做「我的反馈」时

小程序端加 `GET /api/feedback/my?pageNum&pageSize`，返回 `statusDesc`、`replyContent`、`replyTime`；
`t_app_feedback` 已有 `idx_member_time`，不需要改表。用户侧只需要「已回复 / 处理中」两态文案，不必暴露后台的四态。

### 6.6 数据看板（可选）

- 按 `type` 聚合：一眼看出是功能诉求多还是 bug 多；
- 按 `status = 0 AND create_time < NOW() - 24h` 算「超时未处理」；
- 内容违规类（`type = 3`）单独一张表，建议 24 小时内必须处理完。

## 7. 两个踩过的坑（新建模块时一定先看）

**① 类名必须带 `App` 前缀。**
sa-base 的 `module/support/feedback` 里已经有一个「意见反馈」，同样叫 `FeedbackController` / `FeedbackService`。
sa-app 和 sa-admin 都扫 `net.lab1024.sa` 包，同名会让 **应用直接启动失败**：

```
ConflictingBeanDefinitionException: Annotation-specified bean name 'feedbackController'
conflicts with existing, non-compatible bean definition of same name
```

**② 注入字段名不能叫 `feedbackDao` / `feedbackService`。**
项目统一用 `@Resource`，它**先按字段名匹配**。字段叫 `feedbackDao` 会命中 sa-base 的同名 Mapper，
报「The bean 'feedbackDao' could not be injected because it is a JDK dynamic proxy」。
本模块统一用 `appFeedbackDao` / `appFeedbackService`。

> 这条不只针对反馈：任何新模块取名字前，先在 `sa-base/module/support/` 里搜一遍。
